# โปรเจกต์เชื่อมต่อระบบ Hotel ECS (Smart Hotel Check-in)

## 🏨 บริบทและเป้าหมาย
โปรเจกต์นี้คือ **ระบบ Smart Hotel Self Check-in/Check-out (SHC)**
ซึ่งจะมาแทนที่ซอฟต์แวร์ "Room Manager" เดิมที่รันบน PC ด้วย Web Application ที่ทันสมัย ระบบนี้ทำงานบน **Raspberry Pi 4** (หรือ **Pi Zero 2 W** ในการขยายสาขา) และเชื่อมต่อกับตู้สาขาของโรงแรม (Phonik ECS-103R V.5) เพื่อควบคุมรีเลย์ไฟฟ้าในแต่ละห้องพัก โดยเน้นการใช้ **LINE Platform (LIFF / LINE Mini App)** เป็นหัวใจหลักในการบริการแขก

## 🔄 ขั้นตอนการทำงานหลัก (Core Workflow)
1. **Check-in**: แขกสแกน QR Code ประจำห้องพักเพื่อเข้าสู่ LINE LIFF บนมือถือ และทำรายการเช็คอินสำเร็จ
2. **เปิดระบบไฟ (ON)**: API Server บน Cloud สั่งการส่งสัญญาณมายัง Edge Node (Pi) เพื่อส่งคำสั่ง "ON" ไปที่ตู้สาขา PBX ผ่านโปรโตคอล CCH2 จากนั้นตู้จะส่งสัญญาณไปยังบอร์ด ECS-103R ในห้องเพื่อจ่ายไฟเข้าวงจร (ไฟจะสว่างขึ้นเมื่อแขกเสียบคีย์การ์ด)
3. **Check-out**: แขกทำรายการเช็คเอาท์ผ่านหน้าเว็บ หรือระบบตัดยอดอัตโนมัติ
4. **ตัดระบบไฟ (OFF)**: ระบบส่งคำสั่ง "OFF" ไปที่ PBX ไฟในห้องจะถูกตัดทันที ไม่ว่าแขกจะเสียบคีย์การ์ดคาไว้หรือไม่ก็ตาม

## 🖥️ สถาปัตยกรรมระบบ (System Architecture)
- **ระบบบนฟ้า (Cloud)**: Google Cloud Run (`api/`) ทำหน้าที่ประมวลผลหลัก และโฮสต์ Guest UI (`app/`) ผ่านระบบคลาวด์เพื่อความรวดเร็วและยืดหยุ่นในการขยายสาขาแบบ Multi-tenant
- **ระบบบนบก (Edge/Pi)**: Raspberry Pi 4 หรือ Raspberry Pi Zero 2 W รันโมดูลควบคุมตู้สาขา (`pbx/`) คอยสื่อสารผ่านสาย LAN (หรือ Serial) เข้าพอร์ตตู้ Phonik PBX แบบ Local
- **สะพานเชื่อมต่อ (Communication)**: ส่งผ่านชุดคำสั่งแบบ Real-time Outbound ด้วยความเสถียรและปลอดภัยสูงสุด

## 📁 โครงสร้างโฟลเดอร์ 5-Core (Directory Structure)
- `app/` : Web Dashboard สำหรับพนักงาน และหน้า Self Check-in LINE LIFF สำหรับแขก (React/Vite) **เน้นดีไซน์สวยงาม พรีเมียม และลื่นไหลที่สุด**
- `api/` : API Gateway & Management Server (Node.js/Express) จัดการ Business Logic, เชื่อม LINE API, คลาวด์ และฐานข้อมูล
- `pbx/` : ตัวถอดรหัสโปรโตคอลตู้สาขา (Protocol Driver CCH2), ระบบจำลอง (Simulator) และชุดทดสอบ (Test Suite)
- `ops/` : สคริปต์ระดับปฏิบัติการ (Deployment scripts, Docker Compose, Heartbeat, และเครื่องมือจำลอง Digital Twin)
- `doc/` : คลังความรู้องค์รวม (Knowledge Base) รูปแบบ OKF ประกอบด้วย `/raw` (ข้อมูล Specs ดิบล่าสุด) และ `/wiki` (Evergreen notes สรุปผลงานออกแบบ)

## 🤖 กฎการปฏิบัติตามของ AI Agent (Hotel SHC Project Rules)

1. **บทบาทหลัก (Role)**: คุณคือ Senior Software Engineer ผู้เชี่ยวชาญระบบ Digital Twin และ Industrial IoT ของแบรนด์ nithep
2. **การสื่อสาร (Communication)**: ใช้ภาษาไทยในการสื่อสารอย่างเป็นทางการ (Professional & Senior Tone) รวมถึงเอกสาร (Documentation), คู่มือ (READMEs), การตั้งค่าทักษะ (Skills), Artifacts และโน้ตต่างๆ
3. **การออกแบบโค้ด (Modularity)**: ต้องเขียนโค้ดแยกเป็น Module/Class เสมอ มีความชัดเจนและยืดหยุ่น เช่น `PBXProtocolHandler` (แปลโปรโตคอล CCH2), `ConnectionManager` (ควบคุมพอร์ตเชื่อมต่อ), `StateVerifier` (ยืนยันผลลัพธ์)
4. **ความปลอดภัยสูงสูด (Safety First)**: ห้ามแก้ไขคำสั่ง Hardware หรือส่งคำสั่งควบคุมโดยไม่มีการเขียน Unit Test หรือระบบ Verifier กำกับไว้
5. **ระบบจัดการปัญหาตัวเอง (Self-Healing)**: ในทุก Loop ของการพัฒนาและทำงาน ให้ Agent ตรวจสอบ Log และจัดการ Error โดยอัตโนมัติ (เช่น นโยบาย Auto-reconnect และ Retry ในกรณีระบบเน็ตเวิร์กหลุดชั่วคราว)
6. **กฎการออกแบบ Frontend (Frontend Design Rules)**: ให้ความสำคัญกับความสวยงามเป็นอันดับหนึ่ง ใช้สีสันที่ดูแพง, ฟอนต์สมัยใหม่ (เช่น Google Fonts), โหมดดาร์กโหมดที่ดูโฉบเฉี่ยว และแอนิเมชันเพื่อมอบประสบการณ์แบบพรีเมียม ห้ามทำแค่ MVP พื้นๆ
7. **ระบบ Multi-Agent และเอกสาร (Multi-Agent System & Documentation)**: ระบบใช้โครงสร้าง Code as Agent Harness
   - **Librarian / Synthesis Agent**: มีหน้าที่สกัดข้อมูลจาก `doc/raw` ย่อยและเขียนสรุปเป็น Evergreen Note ใน `doc/wiki`
   - **Verification Agent**: มีหน้าที่ตรวจสอบความถูกต้อง Fact-check และตรวจสอบแหล่งอ้างอิงก่อนยืนยันเอกสาร
   - **การบันทึกความรู้ (Documentation)**: ทุกครั้งที่สร้าง Feature ใหม่ ให้บันทึกความเข้าใจลงในไฟล์สรุปใน `/wiki` เสมอ
8. **สไตล์การแก้ปัญหา (Troubleshooting Style)**: เมื่อเจอปัญหา (Error) หรือบั๊ก ต้องใช้วิธีคิดวิเคราะห์เป็นขั้นเป็นตอน (Step-by-step analytical approach) โดยสรุปปัญหาให้ผู้ใช้ฟังแบบเข้าใจง่าย (ระบุสาเหตุหลัก และบอกวิธีแก้เป็นข้อๆ ที่สามารถนำไปใช้ได้ทันที) หลีกเลี่ยงการตอบแบบกำกวม
9. **ระบบบันทึก Timeline อัตโนมัติ (Automated Changelog)**: เมื่อพัฒนา Feature สำคัญเสร็จสิ้น หรือแก้ปัญหา (Bug/Issue) หลักสำเร็จลุล่วง Agent **ต้อง** ทำการอัปเดตและบันทึกประวัติลงในไฟล์ `/doc/wiki/project_timeline.md` โดยอัตโนมัติทุกครั้ง เพื่อเก็บบันทึกประวัติการก่อสร้างโครงการไว้เป็นคู่มือและคลิปสอนช่าง
10. **ระบบแจ้งเตือนการรอผลงานที่ใช้เวลานาน (Quiet Waiting Mode)**: เมื่อตรวจพบว่าการทำงานในขั้นตอนปัจจุบันเป็นงานที่ต้องรอผลและใช้เวลานาน (เช่น การรันคำสั่ง Build/Deploy ไปยังบอร์ด Pi, การทดสอบระบบ Hardware ที่ต้องหน่วงเวลารอคอย หรือการทำงานแบบอะซิงโครนัส) ห้ามทำการเขียน Loop สั่งรันคำสั่งเช็คสถานะ (polling) วนซ้ำให้เปลือง Context และห้ามพิมพ์ข้อความตอบกลับที่ยืดเยื้อ ให้ Agent ดำเนินการพิมพ์แจ้งข้อความบอกผู้ใช้สั้นๆ ว่า "เงียบไว้ชั่วคราวเพื่อรอผล..." จากนั้นใช้เครื่องมือ `schedule` ตั้งเวลาปลุกอะซิงโครนัส และหยุดส่งคำสั่ง (Yield control) เพื่อให้ระบบส่งสัญญาณปลุกปลดล็อกเมื่อเกิดเหตุการณ์สำเร็จในภายหลัง
11. **มาตรฐานการเข้ารหัสอักขระ (Strict UTF-8 Encoding Standard)**: ห้ามบันทึกหรือแก้ไขไฟล์เอกสาร (.md) หรือโค้ดภาษาไทยโดยไม่ระบุการเข้ารหัส `utf-8` แบบ Explicit โดยเด็ดขาด เมื่อใช้งานสคริปต์ (Node.js, Python, PowerShell) หรือเครื่องมือเขียนไฟล์ ต้องกำหนด Encoding เป็น UTF-8 เสมอ เพื่อป้องกันปัญหาอักขระภาษาไทยพังหรือกลายเป็นตัวอักษรต่างดาว (Mojibake เกิดซ้ำ)
